# Source-directed secondary test of optional per-step vectors

The primary panel uses a singleton batch, in which the per-step and per-result vocabulary fields can be compared directly. In the release's per-position callback, the full temporary tensor is moved inside the loop over batch items. This motivates a separate secondary question: does every callback for a two-item batch receive one vocabulary row for its own generated token? This targeted test is not part of the original prospective single-input panel.

Use only the same caller's identical prompt repeated twice: protocol prompt 1. Both items use greedy sampling (seed 1701), beam size 1, cap 2, default penalties; run as a single call with both prompts and with the same API asked to split them via max_batch_size=1. Use a singleton as a control. Confirm using prompt 2 with two identical copies, seed 2701, temperature .7 and top-k five, cap two. Use one CPU FP32 worker. Only read public shape/size/presence from the optional callback field, selected ID and scalar, and the current item's own final vector. Do not index empty or ill-shaped callbacks. For every batch item, compare callback step counts, selected IDs and labels to final sequences, verify scalar against log-softmax of its final vector. Check whether the promised per-step vector consistently has one usable vocabulary entry per token ID and whether the same call returned its full result-side counterpart. Record multiple interpretations: a leading batch dimension alone might be intentional, and a field described as optional can be absent when not requested. Only call it an observed delivery inconsistency if unequal availability persists for identical settings with the option enabled, including the split-batch and fresh confirmation controls. Preserve literal response sizes; no security claim.
